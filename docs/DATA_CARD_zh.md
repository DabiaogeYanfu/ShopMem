# M-LoCoMo 数据卡（v0.5）

## 摘要

这是一个制造领域长对话记忆 benchmark 的最小样例，包含设备维护和质量异常两个场景。数据由事件时间线驱动，再以多角色、多会话对话呈现；每个问题均带答案所需的证据轮次。

## 来源与许可

本版本为人工编写的合成数据，CC BY 4.0 仅作为建议发布许可，正式发布前需由项目维护者确认。未使用任何真实工厂记录。

## 安全与隐私

设备、编号、材料和参数均为虚构。内容不构成工程指导，不应直接用于真实设备决策。

## 生成数据（data/generated/*）的门控标注

`generation/generate_dataset.py` 为每个场景生成 5 个 session：阶段 1（假设讨论）是人与人协作对话（`turn_type` 为 `human` | `tool_call`）；阶段 0/2/3/4 是用户与工业 Agent 的 ReAct 式诊断 episode（`turn_type` 为 `user_query` | `agent_think` | `agent_tool_call` | `agent_response`，`speaker_role=industrial_agent`）——Agent 先给出排查计划，依次调用工具排除若干正常项（低密度），直到恰好一次工具调用（`agent_tool_call`，带 `tool_name`）返回真正解释情况的关键数据（高密度），最后综合给出结论。每个 turn 都打上真值标签 `turn_type` 与 `is_low_density`（是否属于应被语义门控丢弃的低信息密度内容，如例行工具返回、Agent 的排查性 think、寒暄、重复确认）。在当前参数下，全库 turn 级低密度占比约 **69%**（`agent_think` 100%、`tool_call` 100%、`human` 约 89%、`agent_tool_call` 约 66%、`user_query`/`agent_response` 均为 0%，`evaluation/run_baseline.py` 的 `gating_stats` 字段可复算）。这个比例刻意偏高：真实工业值班/人机协作对话中，每一条真正携带新信息的报告/核实通常伴随多条例行查询、确认和 Agent 自身的中间推理，门控机制正是为过滤这部分内容而设计——尤其是 Agent 的 think 轨迹本身不产生实际执行效果，理应被门控丢弃；因此该数值是有意的场景设定，不是随机产物，复现实验时应据此校准压缩率类指标的预期基线，而不要把它当作需要消除的噪声。`evaluation/run_baseline.py` 同时校验了 `evidence_turns_mislabeled_low_density == 0`，即每题的证据轮次永远不会被标记为低密度，门控真值标签内部一致。

`tool_evidence_recall` 问题类别专门测试检索系统能否从一串"正常"工具返回中精确定位那一条带来结论的高密度证据轮次：其 `evidence` 字段指向具体的 `agent_tool_call` 轮次（而非综合结论所在的 `agent_response`），标准答案精确到该轮返回的具体数值/指标（如"振动值回升至3.8mm/s，超过报警阈值2.5mm/s"），不接受笼统结论。

## v0.2 新增：生产日历、班次问题与不可回答题

- **生产日历**：`production_calendar.json` 给出每个 site 的班次日历，session 的 `site_id` 用于查找。阶段 0/2/3 的 `user_query` 用“本班 / 上一班”说明事件发生时间，对应轮次带 `resolved_time`（发生时刻）和 `resolved_shift`（班次 ID，格式为“班次开始日期 班次名”，例如夜班 2026-04-04 20:00 至次日 08:00 记作 `2026-04-04 夜班`）。
- **`shift_temporal`**（300 题）：`evidence` 指向带班次表达的 `user_query`，标准答案是班次 ID 加时段。只用绝对时间戳做归一化的系统，会把凌晨发生的夜班事件记到错误的日期上。
- **`unanswerable`**（300 题，`answerable=false`，`evidence=[]`）：三种类型各 100 题，记录在 `answer.aux.unanswerable_type` 中：`unseen_entity`（编号尾号 101–200，任何场景都没有使用）、`unrecorded_attribute`（供应商、费用、客户，对话中从未出现）、`false_premise`（第三次调整、验证后复发、第二次返工）。标准答案为“无相关信息”。
- **跨轮指代**：带 `resolved_entities` 的 `user_query` 中，约 80 条的高密度内容只用指代词提及实体，实体名只出现在前一条低密度轮次中（该轮不属于证据）。
- **约束与待办写进对话**：v0.1 的任务约束和待办只存在于 `working_memory.jsonl`，而且使用对话中从未出现的 EQ_xxxx 原始编号，导致 `constraint_recall` 的 300 题从历史中无法作答。v0.2 在阶段 3 由工程师说出两条约束，在阶段 4 说出待办“归档处置记录”（原来的待办是“完成验证”，与阶段 4 的“验证通过”矛盾）。`constraint_recall` 的证据指向约束轮次，标准答案包含全部两条约束。
- `evaluation/check_generated.py` 校验以上标注与对话内容一致，包括工作记忆中的每条约束和待办都能在对话中找到原文。

## v0.3 修正：题目与标准答案不一致（对话内容不变）

v0.2 的五类题中，标准答案与对话或与问题本身不一致，导致拿到全部历史的 full_context 也只有 0–7% 的评判准确率。v0.3 只改题目措辞与标准答案，对话、证据、事件和题目编号逐字节不变（v0.2 备份在 `_backup_v0.2/`）；各类题模板数不变，随机数序列不受影响。

- **constraint_recall**：v0.2 问“现在/当前有哪些约束”，但 as_of 时任务已验证通过、可以关闭，约束已满足；改为问任务处理期间登记过哪些约束，标准答案不变。
- **cross_role_dependency**：v0.2 标准答案写死“一线人员先报告，负责工程师验证”，但每个场景阶段 0 的报告人与阶段 4 的提请人都是维修工程师（角色按 session 序号分配）。标准答案改为对话中的实际角色（“维修工程师最先报告……最后由维修工程师提请确认，Agent 经工具核实……”），题目改为不预设角色的问法。
- **superseded_fact**：v0.2 问“哪个早期假设/判断被证明是错的”，标准答案却是被取代的处置措施；对话中唯一的早期假设（阶段 1）后来被证实。题目改为问被取代的处置措施。
- **生效措施去掉过渡状态**：`temporal_order`、`failed_intervention`、`superseded_fact`、`conditioned_parameter` 的标准答案引用阶段 3 措施时不再带“等待连续运行验证”等当时的过渡状态（as_of 时验证早已通过，正确回答“已验证”会被判为矛盾）。
- **working_memory_snapshot**：标准答案改为任务的最新状态（阶段 4）加待办；v0.2 同时列出已被取代的“等待验证”事实和已满足的约束。`working_memory.jsonl` 的 `active_facts` 相应只保留阶段 4 的事实。

## dev_ext：K=30 调参集（2026-09-29 新增）

原 dev 只有 10 个场景，最多只能拼出 K=10 的历史，而主实验在 K=30 下进行。为了在同样长度下调参且不接触 eval，生成器的场景数从 100 增加到 120，第 101–120 号场景写入 `data/generated*/dev_ext/`（20 个场景、780 题，四个领域各 5 个）。生成器按顺序消耗随机数，所以原有 train/dev/test 以及全部 `data/long/{eval,dev}` 文件逐字节不变（已用 md5 核对）。dev_ext 的显示编号尾号为 301–320，对应的 unseen_entity 仿冒编号尾号为 401–420，与已有场景及其仿冒编号都不重叠。新增的 pool `dev30` = dev + dev_ext，只构造 K=30（1 条历史、150 个 session、1309 轮、1170 题，规模与 eval K=30 的三条历史相当）。论文报告的数据集统计仍以前 100 个场景为准，dev_ext 只用于调参。

## test_ext：可训练方法的 K=30 测试集（2026-09-29 新增）

v2 方法（ShopMem-Writer）要在 train 上训练写入模型，而 eval pool 由 train + test 组成，训练后不能再用于评测；原 test 只有 10 个场景，最多拼出 K=10。因此生成器的场景数从 120 增加到 200，第 121–200 号场景写入 `data/generated*/test_ext/`（80 个场景、3120 题，四个领域各 20 个）。生成器按顺序消耗随机数，已有的 91 个数据文件（train/dev/test/dev_ext 及全部 `data/long/{eval,dev,dev30}`）逐字节不变（已用 md5 核对）。test_ext 的显示编号尾号为 601–680，对应的 unseen_entity 仿冒编号尾号为 701–780，与所有已有编号区间（1–100、101–200、301–320、401–420）都不重叠；已核对中英文各 200 道 unseen_entity 题的仿冒编号均不出现在任何对话中。新增的 pool `test90` = test + test_ext（90 个场景，均未用于训练或调参），只构造 K=30：中英文各 3 条历史（每条 150 个 session，1304–1373 轮），共 3510 题，与 eval K=30 规模相同。v2 的主表和消融都在 `test90` 上评测，所有基线在该池上重跑；v1 在 eval 上的结果不与 v2 数字混用。

划分用途汇总：train（80）训练写入模型；dev + dev_ext（`dev30`）调参与选 checkpoint；test + test_ext（`test90`）只用于最终评测。

## v0.4 修正：场景内容一致性与标准答案（2026-09-29，对话与问题全部重新生成）

v0.4 之前做了一次四层数据审核：分布一致性、结构不变量、模板新颖度（`evaluation/audit_splits.py`，均通过），以及 LLM 逐场景、逐题审核（`evaluation/audit_gold_llm.py`）。LLM 审核覆盖 v0.3 中文 test90 全部 90 个场景，逐题审核了部分场景：gpt-6-sol 审 475 题，gpt-6-luna 审 676 题，结果存于 `results/data_audit/v0.3_{sol,luna}/`。审核发现的主要是生成器层面的系统性问题，v0.4 逐项修正：

- **时间倒置**：关键工具返回的"检测时间"原本取查询那一轮的时间，晚于用户已报告的结果。现在取事件发生时间（阶段 0/2/3，与用户所说的班次一致），或验证会话之前的时间（阶段 4）。
- **故障与修复不联动（维修）**：原来各阶段读数固定，与部件无关，例如振动故障却靠更换温度传感器修好，温度先报正常、修复时又说"更换前 82°C"。现在按部件分为 5 个故障族，报警症状、失败措施、各阶段读数都随部件变化；传感器类故障用手持仪表交叉验证。
- **例行排查查询了问题本身**：原来会先报告"批次关联核验正确"，随后又发现"一箱无法匹配"。现在每个领域新增 3 个与问题无关的中性工具，例行排查不再调用问题相关工具。
- **领域流程不合理**：质量场景不再放宽验收阈值，也不再靠设备设定"修好"已生产的批次，流程改为隔离 → 临时上调预热、返工失败 → 更换预热传感器并校准、返工复检合格 → 放行前复检。工艺场景的首件确认按检验项目判定，过程能力复核使用 Cpk 工具。物流场景统一为 12 箱，最终由盘点确认。
- **角色**：每个领域设一个负责角色（维修工程师、质量工程师、工艺工程师、操作员），负责首次报告和提请结案；标准答案不再写入并非说话人的角色。约束由一人提出，由另一人确认；"谢谢提醒"只用于回应真正的提醒。
- **时间线**：5 个会话从跨 5 个月压缩到约 2 周；72 小时连续运行验证放在修复至少 4 天之后；批次号中的年月与首次报告月份一致；删除了与"上一班"前缀冲突的"刚才"，以及不准确的"开班后不久"。
- **工单状态**：用户在最后阶段提请结案（"可以关闭"），Agent 核实后给出结论，不再出现"已关闭"与"可以关闭"并存。
- **标准答案与问法**：superseded_fact 和 temporal_order 明确指"失败的措施"（在质量场景里，"最初的措施"其实是隔离）；failed_intervention 的标准答案只保留失败的措施；multi_hop_event 以"验证通过"为终点；质量场景的 conditioned_parameter 包含隔离；cross_role_dependency 只问首报和最终确认；shift_temporal 和 tool_evidence_recall 的阶段 3 问法去掉了"真正处理好/修复被确认"这类歧义。质量场景现在合理地出现了"返工"，所以 false_premise 题改问从未发生的"第二次停线整改"。

`evaluation/check_generated.py` 新增 v0.4 不变量检查：测量时间不晚于报告并等于发生时间、72 小时验证位于修复之后、例行排查不查询问题工具、首报与结案由领域负责角色完成、批次号月份一致。全部 200 个场景中英文均为 0 错误。数据规模不变（每场景约 44 轮、低密度轮次约 66%、低密度 token 从约 50% 降到约 47%），见 `data/long/STATS.md`。v0.3 数据保留在 git tag `data-v0.3`；所有 v0.3 上的实验结果都不与 v0.4 混用。

## v0.5：结构化 Agent 轨迹、一年期历史与第二轮标准答案修正（2026-09-29）

**Agent 轨迹结构化。** 每次工具使用拆成两轮：`agent_tool_call` 是 Agent 发出的 JSON 请求（`{"tool", "args"}`），`tool_observation` 是工厂系统（EMS/MES，`speaker_role=system_tool`）返回的 JSON 记录，字段包括 `request_id`、`tool`、`status`、`target`、`measured_at`、`data`、`limits`、`result`、`data_quality`、`message`。结构和数值在中英文版中相同（`generation/tool_json.py`），只有 `message` 这一句摘要分语言。例行排查的观测全部正常，属于低密度；每个 episode 恰有一条关键观测为高密度，其 `measured_at` 是被报告事件的测量时间，`message` 就是 tool_evidence_recall 的标准答案，结构化字段中也带有同样的数值。工具观测现在约占全部 token 的 65%，Agent 相关轮次（think、调用、观测、回复）合计约占 88%；一条 K=30 历史约 11.6 万格式化 token（v0.4 约 5.9 万）。评测框架的 observation_mask 基线改为遮蔽 `tool_observation`。

**时间跨度。** 整段历史改为约一年：各场景的首次报告分布在 2025-07 至 2026-05，as_of 仍为 2026-06-30。提问时间距证据的中位数从 99 天增加到 196 天，最长 363 天。单个事件改为持续 13–32 天，各阶段间隔不等（失败措施可以数周后才复发，验证可以在修复一周后才做）。

**第二轮修正**（来自 v0.4 的 luna 审核，结果存于 `results/data_audit/v0.4_luna/`；中文同 18 个场景上，严重问题题目比例从 v0.3 的 38.8% 降到 v0.4 的 24.9%，场景级严重问题从每场景 2.09 条降到 0.80 条）：
- state_tracking 改问"最后一次核实的结论"，不再用"最新状态"（审核把结尾挂着的待办也算作状态）；
- cross_role_dependency 的问法和标准答案都只涉及两个角色；
- constraint_recall 只问登记过的约束，删去"关闭前必须满足哪些条件"一类问法；
- conditioned_parameter 与 superseded_fact 的标准答案标明哪项措施没有奏效、哪项生效并通过验证；
- shift_temporal 的证据加入带测量时间的关键观测；
- false_premise 改问确实不存在的事件（v0.4 的"验证后复发了几次"可以回答为 0 次）；
- 结尾待办从"归档处置记录"（本身属于结案的一部分，与"可以关闭"矛盾）改为"关闭后 30 天内回访复查"；
- 质量场景的设备统一为回流焊炉（此前 AOI 检测站、ICT 测试站和波峰焊都和空洞率、预热、锡膏检查对不上）；
- 跟进问答不再出现"报警未解除却无需现场处理"，也不再声称已写入工单；只做了一项例行检查时，不再说"几项都正常"；提问后缀不再要求"现在的数据"。

`check_generated.py` 新增检查：工具轮次必须是合法 JSON，且 `tool` 字段与 `tool_name` 一致；每条观测之前必须有对应的调用。全部 200 个场景中英文均为 0 错误。

## 已知限制

规模小、合成数据（v2 起训练与评测只使用英文版，中文版保留）、尚未覆盖多模态信号和真实噪声；基线只实现词法检索，不能代表完整记忆系统；`data/generated/*` 的确认语/寒暄短句池规模有限（个位数到十余条），存在跨 session 的字面重复。
